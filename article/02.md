# I Built a Perfume App That Leaves the Gaps Visible

*F-Ray-grance began as a thirty-four-hour build with Claude and Codex. An independent review found seven defects after the tests had passed.*

> A missing note pyramid stays missing. A similar name stays a suggestion. A trait that cannot be derived shows a dash, never a zero.

I own more perfume than I can describe. I know which bottle I reach for on a cold evening. I could not tell you why, or how that bottle relates to the rest of the shelf.

A fragrance app should help with that. But names collide, sources disagree, and note pyramids are missing. An app that fills those gaps by guessing gives me a confident picture of a collection I do not own.

So I built my own. I called it F-Ray-grance. The motto in the spec is *“Don't just track your fragrances. Understand your rotation.”* It runs on my Mac, and the collection belongs to me. Underneath every screen is one rule: if the app does not know something, it says so.

> *All we know is that we don't know*
>
> *How it's gonna be*
>
> — Oasis, *The Masterplan* (1995)

I could write about how quickly the coding agents built it. I also want to write about the wrong fragrance they accepted, the restore they marked as passed too early, and what happened when my Mac went to sleep.

## Thirty-four hours to the first build

The first commit landed on 25 October at 06:26. Phase 14 was pushed on 26 October at 16:23. That first build took just under thirty-four hours. The independent review and the revisions came afterwards.

I started with the documentation: product, architecture, design, data model, persistence, security, operations and quality. Then I split the work into numbered prompts with exit criteria. Each agent had to leave a report and update `state/BUILD_STATE.json` before handing over.

Claude took phases 00–05: preflight, infrastructure, schema and API, Vault and owner security, exact fragrance identity, and the Nuxt shell. Codex completed 06–10: collection workflows, DNA and Compare, local embeddings, seasonal DNA, portability and the release gate. Claude returned for 11–14: the Academy and redesign, images, My Spectrum and the sidebar order.

I used one repository writer at a time. The shared state records who is working, which phase is in progress and which phase last completed. Every commit goes through `./scripts/commit_gh` with explicit paths. Database backups, Terraform state and secrets stay outside Git.

The documentation validator checks the frozen files, prompt registration and links. It cannot tell me whether a restore receipt tells the truth. That took a separate review.

After phase 14, I asked Codex to check whether the prompts had been implemented properly. Its review became phase 15, which Claude executed. Phase 16 added a clean-slate operation. There are now seventeen numbered phases, 00–16, and eighteen architecture decisions. The last successful phase is 16.

## A Vault lab in disguise

Underneath the perfume, this is the same kind of stack I build for Vault demos, scaled down to one Mac.

Caddy listens on loopback and routes requests to a Nuxt 4 frontend or a Fastify API. The API uses PostgreSQL 18 with pgvector. Ollama provides local embeddings. Terraform manages the rootless Podman infrastructure in two roots: one protects the persistent volumes; the other manages the containers and network. Ansible configures the services. Make is my front door for starting, checking, backing up and repairing the stack.

I had a shared Vault running for other labs on the same machine. Pointing at it would have been convenient. I wrote ADR-008 instead: F-Ray-grance gets its own `fray-vault`, initialised by Ansible, with the root token revoked after bootstrap.

The API never sees a static database password. Vault Agent authenticates with AppRole and renders PostgreSQL credentials with five-minute leases. The API watches the rendered file and swaps its connection pool when the credentials change. Its runtime role can read and write application data, but cannot create tables, drop them or rewrite collection history.

I sign in with a password hashed using Argon2id. There is no public sign-up; I create the account on the Mac with `make owner-create`. Sessions use cookies and CSRF protection. The phase 03 security probe recorded 39 passing checks, including lease revocation, pool rotation, a Vault outage, access controls and scans for credentials in project logs.

That is quite a lot of infrastructure for a perfume shelf. It is also the infrastructure I wanted to practise operating.

## CK One Essence is not CK One

The hardest problem in a fragrance app is knowing which fragrance I am looking at.

Dior Sauvage exists as an Eau de Toilette, an Eau de Parfum, a Parfum and an Elixir. They smell different. Calvin Klein has CK One, CK One Essence and a long list of flankers. A search API can return several of them for the same query. Taking the first result would put bottles in my collection that I do not own.

The resolver checks the brand, exact name and any known concentration against Scento, the perfume data provider. A verified identity can still have missing facts. Boss Bottled Elixir, for example, can be identified while its concentration remains unknown in that source. Anything that fails the identity check stays a suggestion with a “Check this one” button. Pressing it runs the check again.

Scento's listing for CK One linked to the brand page instead of the fragrance page. I added a derived `<name>-<house>` slug for that case, but the resulting page still has to pass the same check.

Then I typed the barcode from my own bottle of CK One Essence. Open Beauty Facts named the product correctly. Scento did not list it. The app offered CK One as a suggestion and left it there. That was the correct answer, even if it was not the one I wanted.

![Discover showing the CK One Essence barcode hint from Open Beauty Facts above separate Scento suggestions.](screenshots/02/discover-ean-desktop.png)

*A barcode supplies a product-name hint. None of the suggestions underneath is claimed to be that product.*

Quick find accepts a name, part of a name, a brand or a barcode. I can read the EAN off every bottle I own, and I wanted it to work the way an ISBN works for books. The app checks barcodes I have already verified, then Open Beauty Facts, then a web search for a product-title hint. It uses that hint to search Scento. When I add a verified fragrance, I can retain the barcode so the next lookup finds it directly.

## The chart has to show the gaps

The first design was navy and gold glass. It looked like a boutique, and it said nothing about the data. In phase 11 I replaced it with what ADR-012 calls the Scent Spectrometer: graphite, white, monospaced labels and phosphor lime for verified identity.

The note profile is drawn as a chromatogram. Each listed note gets one peak, grouped into top, heart and base. The caption explains the encoding: “One peak per listed note. Height follows listed order, not concentration. Source: Scento.”

The peaks are a picture of a list. They do not measure the perfume's chemistry.

In the initial collection capture, several fragrances had no sourced pyramid, so their charts were flat. I considered filling those gaps to make the collection look complete. I left them flat. Later, I added a way to research missing facts, with its own source labels and review step.

![Phantom in Red's detail page with its sourced note profile, derived traits, research panel and private collection controls.](screenshots/02/detail-desktop.png)

*The Phantom in Red detail page. Unsupported traits show a dash. A verified fragrance does not acquire a complete profile merely because its identity passed.*

A method called `sourced-notes-v1` maps listed notes to eleven traits. If no listed note supports a trait, it stays unknown. A zero would claim something different: that the trait had been assessed and was absent.

Compare, My DNA and My Spectrum use the same derivation. Each screen names the method version beside the values, so I can see where the numbers came from. The Spectral F logo came from the same visual idea, with the arms of the letter drawn as emission lines.

## Web research gets the lowest trust

Boss Bottled Elixir had an untiered note list in Scento, but no concentration or pyramid. I wanted a way to fill those gaps without letting a search result overwrite better data.

Every value has a source. My own entries take precedence, followed by official data, provider data and derived values. ADR-013 added “Web research” below all of them.

TinyFish searches and reads at most two pages. The app sends the public fragrance identity, not my collection, ratings or notes. It shows proposed facts beside their source page and supporting quote. I accept or reject each proposal. Accepted research can fill a gap; it cannot replace a higher-precedence value. The API key lives in Vault and reaches the API through Vault Agent.

![The lower-trust Web research panel listing missing facts and explaining what is sent before a run starts.](screenshots/02/research-panel.png)

*The research panel at rest. Starting a run may use TinyFish credits; the panel says so before I press the button.*

The first version hung for nineteen minutes.

I had configured a maximum duration and an abort timeout. Neither stopped the request as expected. Meanwhile, the local port forwarder cuts idle connections after about sixty seconds, so even a two-minute run could outlast the browser's connection.

I changed research into a background job. The API starts the run, polls its status and cancels it at 120 seconds using an explicitly retained timer. The browser polls the job instead of holding one long request open.

Live use then found a different problem. Research proposed “Eau de Parfum” for my verified Sauvage Eau de Toilette, and I had already saved it. I added a concentration check and superseded the wrong value. Its history remains visible as replaced.

The independent review later found that the broader identity rule was still too weak. “Sauvage” was a phrase inside “Sauvage Very Cool Spray”, so a page about the latter could supply facts for the former. Asking the research agent whether it had found an exact match had not prevented that.

Phase 15 replaced that shortcut with one shared rule for research, web image search and barcode-name labels. After allowing for the exact name, house, compatible concentration, size and a small set of packaging words, unexplained qualifiers cause rejection. The server checks this itself.

It is strict enough to reject a title such as “Boss Bottled Elixir Parfum Intense” because of the extra “Intense”. I may get fewer results. Rejected pages show the reason, and I can decide whether to enter a fact myself.

## Passing tests missed seven defects

When Codex reviewed phases 01–14, all 49 existing browser tests passed. It still found seven defects by reading the implementation and trying cases those tests had not covered.

Two findings were in recovery. A restore could write a PASS receipt before checking its images. If that later check failed, the command failed but the saved receipt still said PASS. A backup could also refer to image files that its archive did not contain. A third finding concerned older backups: a valid archive could fail because the restore code assumed newer tables already existed.

The remaining findings covered the fragrance identity shortcut, unregistered prompt files, a race on My Spectrum and missing Spectrum interactions. If I switched scope while a request was slow, its late answer could replace the result for the scope I had just selected. Plotted ticks also lacked their promised links, and a collection marker based on one fragrance needed to say so.

Claude implemented the revisions in phase 15. Restore attempts now write one receipt at the end, and it says PASS only after every stage passes. Backups check their image references before publishing a recovery set. Restore tests unpack into a fresh image volume, verify and decode the files, and check that each image is visible only to its owner. Older schemas are upgraded inside the disposable restore target after migration-history checks; newer, unsupported schemas are refused.

The recovery matrix added eighteen cases, including corrupt archives, missing image files, older schemas and failed stages that must never leave a PASS receipt. Seven new browser tests covered the Spectrum revisions. The completed phase recorded:

- 210 API tests passing;
- 35 web unit tests passing;
- 56 browser tests passing;
- 18 recovery-matrix cases passing.

Those are the recorded validation results, not a fresh run for this article. The original tests had passed too. The review gave me specific failures to reproduce and add to the checks.

## What my collection can tell me

Compare stays limited to two fragrances. It starts with “What differs?” and uses only sourced information. Underneath is a sentence I wanted there from the start: “A note not listed on one side is not proof of its absence.”

![Compare showing Phantom in Red and Layton, their listed differences and side-by-side scent traits.](screenshots/02/compare-desktop.png)

*Phantom in Red against Layton. The app contrasts known scores and leaves unknown ones as dashes.*

My Spectrum describes the collection on two axes, Fresh to Warm and Dry to Sweet. A fragrance is placed only when both ends of an axis have known supporting traits. The collection marker is the unweighted mean of the placed fragrances, with a band for their spread. Ratings do not affect it, and several bottles of one fragrance count once.

Coverage is part of the result. If only two of six fragrances can be placed, I need to see that before interpreting the marker. After phase 15, a marker based on one fragrance says so. Ticks open the fragrance, and overlapping ticks open a short list I can use with a mouse, touch or keyboard.

![The current My Spectrum page with one demo fragrance, clickable plotted ticks and the label “based on one fragrance”.](screenshots/02/spectrum-desktop.png)

*A fresh capture after the revisions, using one owned Layton on a temporary demo account. One placed fragrance is labelled as one fragrance.*

The page describes what is in my collection. Owning several fresh fragrances does not establish that I prefer them. I might have bought them years ago, received them as gifts or stopped wearing them.

The Scent Academy is where I can learn something beyond the catalogue. It has six short, original lessons, plus a note explorer, a family explorer and a glossary. Train My Nose is private blotter practice: smell at the opening, around twenty minutes and around sixty, and write down what changed. It is never scored.

![The Scent Academy learning path, Train My Nose and reference explorers, with synthetic progress on a demo account.](screenshots/02/academy-desktop.png)

*The Academy with one lesson completed and one in progress on the demo owner.*

The tutor can use a local generative model through Ollama if I configure one. I have not configured that optional model. The app says it is unavailable and keeps the curated lesson material usable. Local embeddings are a separate feature; having them running does not mean the tutor can answer questions.

## Then my Mac went to sleep

The incident I learned the most from had nothing to do with perfume.

The Podman VM runs on my MacBook. When the Mac sleeps, the VM pauses. On waking, its wall clock can lag until chrony steps it forward. I measured a lag of 27 minutes once.

Vault sees the corrected time and expires the five-minute database lease. Vault Agent schedules renewal against the guest's monotonic clock, which did not advance through sleep in the same way. It can still believe renewal is minutes away. The API is then holding a revoked login, and my collection page showed “Internal error”.

I first shortened the lease and documented `make heal` as recovery. Eventually I added a small supervisor around Vault Agent. Every ten seconds it compares elapsed wall time with elapsed `/proc/uptime`. A difference greater than thirty seconds restarts the agent. It authenticates again, renders fresh credentials, and the API replaces its pool.

I verified two real clock jumps, 1,892 seconds and 1,190 seconds. Both recovered in two to three seconds.

That same afternoon I got a 500 from a healthy stack for a completely different reason. A PostgreSQL query checked that a JSON value was an array and then checked its length, joined by `AND`. I had read that as a safe sequence. PostgreSQL does not promise to evaluate those operands left to right. It tried to take the array length of a JSON null.

The fix was a `CASE`, with a comment explaining why it must stay. I do not want a coding agent, or future me, tidying that back into the broken version.

## I also need to be able to empty it

Collection history is append-only. Status changes become new events, and a database trigger rejects updates and deletes. That preserves a record of what I owned and when.

It also meant that once I added a perfume, I could never take it out. A collection I can only add to stops being a record of what I own.

Migration 0007 introduced a narrow removal function. It runs with the table owner's permissions and authorises deletion for one entry in one transaction. The normal API login cannot assume that role. Before removal, I see what will go and what will stay, then confirm it. Linked training notes survive as generic blotter practice. A deletion log keeps counts and flags, without retaining the text I asked to remove.

There are now two broader reset commands:

- `make purge` empties one owner's personal data while keeping the account and shared catalogue.
- `make clean-slate`, added in phase 16, empties personal data for every owner and the shared catalogue, while keeping accounts, credentials, migration history and the seeded lessons.

Both require typed confirmation and a fresh backup before changing anything. The clean-slate operation was tested against an isolated copy; building the command did not mean running it against my live collection.

Deleting an image now removes its database record first. The file stays until a later manual backup collects unreferenced files older than an hour. That change came from the recovery review: a file might still be needed by another owner or by the snapshot being backed up.

## Ready for a phone, still local to my Mac

The layout is tested at 390 pixels. The sidebar becomes a drawer, the most-used destinations move to a bottom bar, and the note profile keeps its three tiers in the narrower frame.

![The collection at a 390-pixel phone viewport, with compact rows and bottom navigation.](screenshots/02/collection-mobile.png)

*The phone layout in a browser capture. This does not demonstrate access from my iPhone.*

The phone does not reach the app yet. I installed Tailscale, but my employer's DNS policy blocked it as a personal VPN. I chose not to work around a corporate control for a perfume app. ADR-009 records that deferral, and the app stays on loopback.

Phase 10 originally required off-device protection and a restore on a second machine as well. Local restores could not satisfy those requirements, so the phase remained blocked while I kept developing locally.

I later changed the acceptance scope explicitly. ADR-018 marks phase 10 completed for local operation, based on its security, lifecycle and isolated-recovery evidence. The state now records phase 16 as the last successful phase.

Three things remain deferred and untested:

- iPhone access through Tailscale;
- a protected off-device backup copy;
- a restore on a second machine, outside the original Podman VM.

Completing the local scope did not produce that evidence. Local backups and isolated restore tests cover mistakes I can make on this Mac; I have not proved recovery after losing the Mac. Bulk import stays disabled. I add fragrances through the app.

Somewhere in my cabinet there is a bottle of Boss Bottled Elixir. When Scento did not list its concentration, I added a way to research it and review the result. For CK One Essence, I had a barcode hint but no verified Scento identity. I left CK One in the suggestions.
